# `gpt_sovits_text::tone_sandhi` parity

Port of `GPT_SoVITS/text/tone_sandhi.py` (GPT-SoVITS `04a44eb`, from
PaddleSpeech, Apache-2.0) in `crates/ports/gpt_sovits_text/src/tone_sandhi.rs`.

## Ported scope

| Python | Rust |
|---|---|
| `ToneSandhi.__init__` (`must_neural_tone_words`, `must_not_neural_tone_words`, `punc`) | `ToneSandhi::new` (fields with the same names; the set literals are also `MUST_NEURAL_TONE_WORDS`, `MUST_NOT_NEURAL_TONE_WORDS`, `PUNC`) |
| `_neural_sandhi`, `_bu_sandhi`, `_yi_sandhi`, `_split_word`, `_three_sandhi`, `_all_tone_three` | same names |
| `_merge_bu`, `_merge_yi`, `_merge_continuous_three_tones`, `_is_reduplication`, `_merge_continuous_three_tones_2`, `_merge_er`, `_merge_reduplication` | same names |
| `pre_merge_for_modify`, `modified_tone` | same names |
| `str.isnumeric()` | `py_isnumeric` (Python 3.11 / Unicode 14.0.0 table, generated by `gen_isnumeric_table.py`) |

Nothing in the file is left out.

Differences in form, not in behaviour:

- Where Python raises `IndexError` (a final list shorter than the word, an
  empty final string such as `lazy_pinyin("嗯")` -> `[""]`, an empty `pos`,
  an empty word in `_split_word`), the Rust method returns
  `IndexError("list index out of range")` or
  `IndexError("string index out of range")`, the Python message.
  `_merge_bu`, `_merge_er`, `_merge_reduplication` and `_is_reduplication`
  cannot raise and return plain values.
- `pre_merge_for_modify` catches the errors of `_merge_yi` and the two
  three-tone merges, prints `"<name> failed"` to stdout and keeps the seg, as
  the bare `except:` in Python does. The `_merge_yi` error path is
  unreachable in Python too.
- Python mutates the caller's `finals` list. Rust takes `finals` by value and
  returns what the Python method returns.
- A seg is `Vec<(String, String)>` (`Seg`); Python mixes tuples and lists.
- `ToneSandhi::cut_for_search` holds the module-level
  `jieba.cut_for_search` (default `jieba_fast::cut_for_search(word, true)`),
  so callers and tests can replace it like a Python monkeypatch.

## Fixtures

`gen_fixtures.py` writes `crates/ports/gpt_sovits_text/tests/fixtures/tone_sandhi/`
(about 3.1 MB):

```sh
pixi run --manifest-path crates/ports/gpt_sovits_text/pixi.toml fixtures tone_sandhi
```

Inputs are 5662 texts: 107 hand-written texts aimed at each rule (不 / 一
variants including numbers, ordinals, `V一V`, punctuation after 一,
reduplication, 儿, neutral-tone particles and suffixes, 个 as measure word,
must-neutral and must-not-neutral words, three-tone runs and splits, empty
finals, punctuation), the 155 texts of `parity/corpus/gpt_sovits_zh_en_yue.json`,
5200 random sentences of jieba dictionary words mixed with sandhi triggers
and 200 random runs of characters biased to tone three (seed `20251102`).
Each text goes through the `chinese2.py` steps that run before `ToneSandhi`:
`text_normalize`, the sentence split of `g2p`, `re.sub("[a-zA-Z]+", "")` and
`jieba_fast.posseg.lcut`. That gives 6653 segments.

- `pre_merge.jsonl`: `pre_merge_for_modify(seg)` and the failed merge steps
  per distinct seg (plus hand-written segs).
- `modified_tone.jsonl`: `modified_tone(word, pos, finals)` for every word
  of every merged seg, with finals from `lazy_pinyin` (as
  `chinese2._get_initials_finals`) and, where they differ, also the finals of
  the G2PW branch of `chinese2._g2p` (punctuation as its own final, G2PW
  readings). Plus hand-written words with odd finals.
- `units.jsonl`: every method on the hand-written cases and on a fixed-seed
  sample of the bulk inputs.
- `split_word.jsonl`: Python `list(jieba_fast.cut_for_search(word))` and
  `_split_word(word)` for every word in the other fixtures.

Every line of `tone_sandhi.py` from `_neural_sandhi` on runs on these inputs,
except the unreachable `except:` of `_merge_yi`.

## Parity

The tests run `ToneSandhi` with `cut_for_search` replaced by the recorded
Python output, so they check the tone sandhi logic independently of jieba:

| Fixture set | Cases | Exact matches |
|---|---|---|
| `pre_merge.jsonl` (output and failed steps) | 6439 | 6439 |
| `modified_tone.jsonl` | 16684 | 16684 |
| `units.jsonl` (13 methods) | 4377 | 4377 |
| `split_word.jsonl`, recorded `cut_for_search` | 15160 | 15160 |

With the real `jieba_fast` port (`crates/ports/jieba_fast`, a port of
jieba_fast 0.53 with its own parity fixtures):

| Fixture set | Cases | Exact matches |
|---|---|---|
| `jieba_fast::cut_for_search` vs Python | 15160 | 15160 |
| `_split_word` | 15160 | 15160 |
| `modified_tone` | 16684 | 16684 |

`KNOWN_SPLIT_WORD_MISMATCHES` in `tests/tone_sandhi.rs` is empty. It used to
list 208 words that the earlier jieba-rs wrapper got wrong: runs of
characters that are not in the jieba dictionary, which Python `jieba_fast`
keeps as one HMM word (`cut_for_search("仳涏")` -> `["仳涏"]`,
`lcut("忐睧儿")` -> `["忐睧儿"]`) and the wrapper split into single
characters. The `*_with_jieba` tests fail on any mismatch outside the list.

`gen_fixtures.py` skips the G2PW finals of two words (`挛一`, `挛不`) whose
G2PW pinyin is `None` (`"ㄌㄩㄢ2" cannot convert to pinyin`):
`chinese2._g2p` raises `TypeError` on them before `ToneSandhi` runs.
